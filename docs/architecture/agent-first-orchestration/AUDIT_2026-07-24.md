# Audit: Agent-First Orchestration Plan

**Date:** 2026-07-24
**Scope:** README.md + V0_ARCHITECTURE_PLAN.md, verified against the live codebase
**Method:** Three parallel investigations — (1) claims verification against the existing
runtimes, (2) queue/persistence infrastructure gap analysis, (3) adversarial architecture
critique — synthesized here. All file paths cited were verified in-repo on 2026-07-24.

## Verdict

**Direction: right. Plan as written: not ready to implement.** The diagnosis of the current
system is verified accurate, the architectural hygiene (ports, dependency rules, fitness tests,
state-rows-authoritative) is genuinely good, and the new concepts (agent-first routing, a real
stage/step DAG, typed artifacts, receding-horizon replanning) are real improvements. But the plan
has three structural problems that should be fixed in the documents before Slice 0 starts:

1. **It schedules falsification of its own hypothesis last** (Milestone 6 of 7), violating its
   own Principle 9. The hypothesis is about model behavior and can be tested in ~1–2 weeks with
   no database, queue, or UI.
2. **It draws the "don't reuse" boundary around infrastructure instead of cognition**, planning
   to rebuild durable-execution machinery that landed in this repo, committed and deployed, one
   day before the doc was written — plus ports that already exist by the exact proposed names.
3. **~8 contract holes block the Slice 0 deliverables** (the compiler, state machines, and join
   semantics cannot be implemented as specified).

## 2. Course correction: falsify first (biggest change)

Milestones 1–5 build contracts, a simulator, a durable kernel with leases/fencing/RLS, agents,
and a new API+UI surface before Milestone 6 produces the first comparative measurement. The
product hypothesis — *small orchestrator + specialists beats one context-heavy agent on complex
work without making simple work slow* — requires none of that to measure.

**Recommended replacement sequencing:**

**Phase A — falsification harness (~1–2 weeks, no DB, no queue, no UI):**
- Freeze ~8 scenarios drawn from **real production chat sessions** (`chat_sessions` /
  `chat_turn_runs`) plus a frozen project snapshot
  (`tests/integration/fixtures/deep-research-base.sql` is the precedent).
- Implement CEO route mode as a single function; score routing accuracy against hand labels.
- Implement "workflow" as plain in-process async: `Promise.all` over specialist calls → digest
  builder → transition call → synthesis. No persistence, no leases, no events.
- Control lane: the existing `pnpm test:agentic` harness
  (`apps/web/src/lib/tests/agentic-e2e/`) already drives the real stream endpoint with scenario
  files. It is the control, already built.
- **Pre-register the decision rule before running** (see §6, B8).

**Phase B — only if Phase A wins:** build the durable kernel, adding only the genuinely new
tables (see §3), inheriting the execution substrate.

This ordering also de-risks the highest-uncertainty product question: whether route accuracy is
achievable from a "lightweight world card" at all (requests like "what's blocking the launch?"
sound direct but require many reads).

**Genuinely new (the real build):** normalized run→stage→step→dependency DAG persistence
(nothing like it exists — `orchestration_state` is a JSON blob consumed only by
`deepResearchOrchestrator.ts`), the typed/versioned **artifact store** (confirmed gap: deep
research's report lives only in `agent_runs.result.answer` JSONB), the stage compiler, the CEO
route/transition prompts, and the agent catalog/manifests.

**Caveats on reuse (do not over-rotate):**
- Every fencing/dispatch/cap primitive is hand-coded against one table — extraction into generic
  form is real work the plan should budget explicitly, not assume.
- Whether to reuse the `agent_runs` **row** itself (e.g. `run_template='orchestrated'`) vs. a
  separate `orchestrator_runs` table is genuinely uncertain: `agent_runs` is shaped for a single
  loop and deep-research triggers/CHECKs hardcode exactly 2 children. **Recommended: a 1-day
  spike** — add an orchestrated run + the 4 new tables without touching any existing
  deep-research constraint. If that fails, keep separate tables but copy the
  events/signals/receipts/cost-ledger schemas and RLS verbatim.
- Known open queue bugs the new system would inherit and must design around:
  completion-RPC failure re-executes a successful job (N8 — direct threat to "wake the CEO
  exactly once"), tokenless bypass on complete/fail RPCs, strict priority with no aging, and a
  **single worker process with 10 global slots across 17 job types** — a 4-way fan-out consumes
  40% of prod worker capacity. Caps must be domain-level, not queue-level.

## 4. Contract holes to fix in the docs before Slice 0

- **B3 — ContextPacket contradiction.** `StepAssignment.context_packet_id` (bound at assignment,
  immutable) vs. per-agent context builders vs. librarian-produced packets forces
  librarian-first serialization: every "parallel" workflow degrades to
  `Stage 1 = librarian alone → gate → Stage 2 = fan-out`, adding an LLM stage + CEO wake to
  nearly everything. **Fix: delete `context_packet_id`;** a context packet is just an artifact
  consumed via `input_artifact_ids`; baseline orientation comes from the manifest's
  deterministic context builder. Consider a **deterministic (non-LLM) librarian for V0** — it
  tests the bounded-context hypothesis with one less LLM call and one less stage.
- **B4 — `StepSpec` is never defined.** The compiler (a Slice 0 deliverable) has no input type.
  Needs a field-by-field table: model-authored (`StepSpec`) vs. policy/compiler-derived
  (`StepAssignment` — `permission_grant`, `budget`, `timeout_ms` are policy outputs per §10).
- **B5 — State-machine holes.** (a) `waiting_decision` is on the only path to stage `completed`,
  and under receding-horizon planning a non-gated stage has nothing to continue to — in V0
  `decision_gate` is effectively always true; say so and budget one CEO call per stage.
  (b) The join×failure matrix (`all|best_effort` × `replan|complete_partial|fail`, incl.
  best_effort-with-all-failed) has no truth table — write the 6 rows. (c) Step-level
  `needs_input` is unimplementable (only the CEO talks to the user; assignments immutable) —
  delete it; use `partial` + `open_questions`, CEO escalates at the gate. The existing system
  correctly puts `needs_input` at run level.
- **B6 — No session/run model; `clarify` has no resume contract.** A route-time `clarify`
  produces no stage, so the answer can re-enter through neither CEO mode. Adopt the existing
  checkpoint pattern: **run ≈ turn** (always terminal), attached to a session; `clarify` ends
  the run with a checkpoint artifact; the answer starts a new run inheriting it. Also: the
  promised direct→workflow promotion has no contract.
- **B7 — Budget units undefined** (and missing from §18). Adopt the existing ledger's answer:
  **USD, reserve-before-dispatch → settle-on-completion, `attempt_key` idempotency.**
  Reservation is mandatory — N parallel steps can each fit the remaining budget and collectively
  blow it.
- **B8 — Eval has no pre-registered decision rule and an ambiguous control lane.** "The existing
  system" is three service trees — name the control (v2 stream path). Write the go/change/stop
  thresholds before running (e.g., workflow lane wins ≥60% of blind complex comparisons at ≤3×
  cost; direct-lane p50 TTFT ≤1.5× current chat — measure the baseline first). 15 scenarios × 1
  run cannot separate signal from LLM variance; use repeated runs on fewer scenarios, built from
  real transcripts.
- **Direct-lane TTFT regression, unacknowledged.** Chat streams text immediately (and has a
  prewarm cache); route mode must complete structured JSON before anything renders, and
  prewarming can't help. Decide the mitigation now (small/fast router model, speculative
  execution, or stream-after-route).
- **Digest bounding.** §6.7 lists ~9 categories with no size cap — this regrows the context
  problem the project exists to escape. Specify a token ceiling, per-summary truncation, and
  deterministic overflow order (failures first, most recent stage first).
- **Replan/stage caps.** `failure_policy: replan` with no `max_replans`/`max_stages` is an
  unbounded loop backstopped only by an undefined budget. Lock `max_replans=2`,
  `max_stages=5`, persist counters.
- **Prompt injection needs an architectural boundary, not just an eval scenario.** Researcher
  web text → artifact summary → CEO digest → CEO authors next stage. Require: untrusted-content
  delimiting + provenance tagging in digests; the user's `objective` is immutable across
  transitions and can never be rewritten from artifact content; §10's server-side grant
  intersection named as *the* escalation defense. Reuse `shared-agent-ops/web/safe-fetch.ts`.
- **Acceptance criteria are self-graded.** `AgentResult.acceptance_results` is the specialist
  grading itself. Require machine-checkable criteria validated by code at step completion —
  `deepResearchEvidence.ts` (rejects claims citing unvisited URLs) is the working precedent.
- **Retention/GC absent.** `agent_run_events`/`chat_turn_runs` are already unbounded (known open
  N18). Lock: JSONB with hard per-artifact cap (~256KB, summary ≤1KB), defer object storage,
  ship a retention job with the schema.
- **Minor:** `reason_code` should be a typed union (it's a measured eval metric); artifact
  codecs must stay read-compatible with persisted `schema_version`s; specify cancel-vs-join
  precedence (terminal states win).

## 5. Factual corrections for the docs

1. **Deep Research is not a peer runtime.** It is a mode inside the Agent Run worker
   (`apps/worker/src/workers/agent-run/deepResearchOrchestrator.ts`, same worker, same
   `agent_runs` table). The Architectural Boundary list should be corrected.
2. **Tree Agent is not cleanly removed, and "removable without a migration" is empirically
   false.** App code was deleted (`c95d3f5b`), but `packages/shared-types/src/tree-agent.types.ts`
   (374 lines, zero consumers) is still exported, and the `tree_agent_*` tables
   (`20260127_090000_tree_agent.sql`) have no down-migration and almost certainly still exist in
   prod. Do the cleanup pass before citing it as precedent.
3. **§17 lesson 5 (heartbeat/duplicate-execution risks) is inference, not documented history** —
   plausible from the code's shape, but stated nowhere in the tree-agent specs. Label it as
   inference.
4. **Tree Agent's actual cause of death is missing from §17.** The 7/01 worker audit's verdict:
   an *orphaned experiment* — UI linked from nowhere, superseded by `agent_run`. It died of
   **non-adoption**, not recursion or event-sourcing. It was ~6,761 LOC and structurally ~80% of
   what this plan proposes. The single most important lesson for this project is therefore a
   product-surface lesson: **do not ship a fifth parallel agent surface** (chat modal, agent
   runs/inbox, project reviews, deep research already exist). Cut Slice 4's new UI; use an admin
   route/raw JSON during evaluation; if the architecture wins, adopt it **inside** the existing
   chat entry point as a routing decision, not a new destination.

## 6. What is genuinely well done — keep as-is

- Ports/dependency rules + architecture fitness tests (the correct answer to the measured bloat).
- State rows authoritative; append-only events for audit/projection only (direct inversion of
  Tree Agent's event-sourced source of truth and its "failed nodes stay running" bug class).
- Permission intersection with re-check at operation time; "model text is never an authorization
  source" (Tree Agent shipped a live cross-tenant hole: empty `allowedProjects` removed all
  project filtering).
- Immutable assignments with replacement-step lineage; "artifact persistence failure prevents
  `completed`" ordering invariant.
- Receipt-aware retries.
- The artifact store concept (new and needed).
- Non-goals list and binary hard safety gates; depth-1 matches the existing
  `agent_runs_depth_range` CHECK.

## 7. §18 open questions — dispositions

- **Q1** (job types): lock now — one job type, discriminated payload (matches existing pattern).
- **Q2** (artifact storage): lock now — JSONB + hard cap; defer object storage.
- **Q3** (direct-lane ops): real question; needs an ADR. Also define `DirectActionSpec` — is the
  direct lane a declarative pre-authorized op list or a mini agent loop? Recommendation: model a
  direct run as one implicit stage + one CEO step (uniform receipts/events/eval lanes).
- **Q4** (concurrency caps): lock now — per-run parallel steps = 3, per-user active runs = 1,
  enforced in domain layer (single-process worker reality).
- **Q5** (pinned eval model): real; small ADR.
- **Q6** (guidance timing): already answered in production — signals drain between iterations
  (wait for next checkpoint). Take that answer.
- **Missing from the list and more important than most of it:** budget units (B7), session/
  clarify model (B6), join truth table (B5), digest bounding, direct-lane receipts, pre-registered
  eval thresholds (B8).

## 8. Decision points

1. **Sequencing:** falsification harness first (Phase A, ~1–2 weeks, in-process, uses existing
   `test:agentic` as control) vs. building the durable kernel first as written. Recommended: A.
2. **Substrate:** spike reusing the `agent_runs` execution substrate vs. fully separate
   namespace. Recommended: 1-day spike, fall back to separate tables with copied schemas/RLS.
3. **Surface:** no new user-facing UI until the architecture wins its eval; adopt inside chat if
   it does. Recommended strongly (this is how Tree Agent died).
