## 1. LLM tool design for tabular data

### 1.1 Serialization: what format to show the model

| Evidence                                                                                                                                                                                                    | Finding                                                                                                                                                                                                                                                                         |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ImprovingAgents, 11-format test (GPT-4.1-nano, 1,000 rows × 8 cols, 1,000 lookup questions) — https://www.improvingagents.com/blog/best-input-data-format-for-llms                                          | Markdown-KV 60.7% acc / 52k tokens; XML 56.0% / 76k; YAML 54.7% / 55k; HTML 53.6% / 75k; JSON 52.3% / 66k; **Markdown table 51.9% / 25k**; JSONL 45.0%; **CSV 44.3% / 19.5k** (worst-but-one). | Table Meets LLM (Sui et al., WSDM'24) — https://arxiv.org/html/2305.13062v4                                                                                                                                 | HTML + format explanation + role prompt was best (65.43% over 7 structural tasks); HTML beat "NL+Sep" by 6.76 pts (GPT-3.5 era).                                                                                                                                                |

Relevant only for messy multi-region sheets. BuildOS tables are rectangular.                                                                    |

**Takeaway:** for rectangular, database-style tables, use a **markdown table** for paged reads. It gives near-best accuracy at about 40% of JSON's tokens. Switch to **markdown-KV record blocks** (`### r12` then `- Status: Done` lines) when rows are wide (more than about 10–12 columns) or cells hold long text. Use JSON only for tool arguments. Avoid CSV for reads.

### 1.2 Read patterns and inline limits

- Accuracy drops with size. Binder, DATER and similar pipelines lose 30–50 pts on tables longer than about 4K tokens (TabScope / survey summary: https://arxiv.org/html/2609.03395). NeedleInATable shows a monotonic decline. NIHT shows 81% at 50×5.
- TableRAG (Google, NeurIPS'24) — https://arxiv.org/abs/2410.04739: for large tables, use **schema retrieval** (column names and types) plus **cell retrieval** rather than encoding the whole table.
- Table-agent survey — https://arxiv.org/pdf/2507.10281: start schema-aware, sample rows, retrieve the affected region before editing, and verify before applying.
- Anthropic, _Writing effective tools for agents_ (2025-09-11) — https://www.anthropic.com/engineering/writing-tools-for-agents: "implementing some combination of pagination, range selection, filtering, and/or truncation with sensible default parameter values"; use a `response_format` concise/detailed enum (72 vs 206 tokens in their example); Claude Code caps tool responses at 25k tokens; truncation should tell the agent how to get more.
- **Rule of thumb:** inline the whole table only if it is about 50 rows × 8 columns or smaller (about 2–4k tokens). Otherwise return schema, column stats, the first page, and aggregates.

### 1.3 Write patterns: identifiers, batching, concurrency, confirmation

- **IDs:** Anthropic: "merely resolving arbitrary alphanumeric UUIDs to more semantically meaningful and interpretable language (or even a 0-indexed ID scheme) significantly improves Claude's precision in retrieval tasks by reducing hallucinations." (same URL as above).
- **A1/positional refs break under edits.** Spreadsheet-RL (2026) — https://arxiv.org/html/2605.22642v1: spreadsheet-native tools (`find_cells`, `inspect_range`, `fill_formula`, `delete_rows`, `recalculate_and_read`) "remove low-level failure modes" such as wrong column indices after deletion. Qwen3-4B went from 12.0% to 23.4% on SpreadsheetBench, and the harness/tools alone gave +7.3 of that.
- **Database-style products use record IDs + field names, not A1.** Airtable MCP: `list_records(filterByFormula, sort, fields, pageSize≤100)`, batch create/update/delete capped at 10 records — https://glama.ai/mcp/servers/medlag/airtable-mcp-server. Notion MCP `notion-query-data-sources`: rows identified by page ID/URL, properties by name, rows mode with two-level and/or filters, default 50 / max 100 rows, plus SQL mode and saved-view mode — https://developers.notion.com/guides/mcp/mcp-supported-tools, changelog https://developers.notion.com/page/changelog (SQL released Jan 15 2026 for Enterprise, expanded Sept 10 2026).
- **Poka-yoke:** Anthropic, _Building effective agents_ — https://www.anthropic.com/engineering/building-effective-agents: "Change the arguments so that it is harder to make mistakes." SWE-bench example: requiring absolute paths, "the model used this method flawlessly". Keep formats close to natural text and avoid counting overhead.
- **OpenAI function-calling best practices** — https://developers.openai.com/api/docs/guides/function-calling: fewer than about 20 functions per turn; enums and structure "to prevent invalid states"; always use strict mode; **"Don't require the model to fill in arguments you already possess"**; merge functions that are always called in sequence.
- **Batch writes:** Google Sheets guidance is to use batchGet/batchUpdate, chunk large writes, and cap rows/cells per write with a dry-run option — https://developers.google.com/workspace/sheets/api/guides/values ; StackAI agent guide https://www.stackai.com/insights/how-to-build-a-reliable-ai-agent-for-excel-and-google-sheets-step-by-step-guide ("read current values before writing", dry_run, caps).
- **Preview/confirm in shipping products:** Excel Agent Mode shows a plan and step list you can review or revert (https://www.windowscentral.com/microsoft/microsoft-office/excels-new-agent-mode-can-fix-your-broken-formulas-proving-ai-can-be-useful , https://sagnikbhattacharya.com/blog/copilot-agentic-ga-2026). Gemini in Sheets (Apr 2026) builds a plan for approval and reports 70.48% on SpreadsheetBench (https://workspaceupdates.googleblog.com/2026/04/build-and-edit-complex-spreadsheets-with-Gemini-in-Google-Sheets.html). Claude in Excel highlights changed cells, warns before overwriting, and edits inputs rather than replacing formulas with values (https://www.datacamp.com/tutorial/claude-in-excel , https://agentscamp.com/guides/analytics/claude-for-excel-guide). Excel Agent Mode scored 57.2% on SpreadsheetBench vs 71.3% for humans (https://petri.com/microsoft-vibe-working-agent-mode-word-excel/).
- **Bulk-agent reliability (vendor benchmark, biased):** GPT for Work ran 11 tests (Mar 2026). Claude in Excel stalled or failed on 100/1,000/10,000-row bulk jobs. Copilot edited unselected tabs and added charts nobody asked for — https://gptforwork.com/blog/ai-agents-for-excel-benchmark. **Implication:** bulk work must be server-side and batched, report progress, and stay scoped to the target.

### 1.4 Query tools: structured args vs model-written SQL

- Weaviate, _Querying Databases with Function Calling_ (Jan 2025) — https://arxiv.org/abs/2502.00032: one structured query tool (search + filters + aggregation + groupby). **GPT-4o-mini 73.7% exact match vs Claude 3.5 Sonnet 74.3%** (GPT-4o 71.8%). Models did well on boolean filters and **struggled with text-property filters**. Structured schemas let small models match big ones.
- Small-model survey — https://arxiv.org/pdf/2510.03847: with explicit schemas and validators, small models often match larger ones on function calling.
- Text-to-SQL risks: hallucinated columns, wrong joins and aggregations (SQLGenie, ACL'25 — https://aclanthology.org/2025.acl-industry.71.pdf). The best model flagged risky queries only 61.7% of the time vs 94% for humans (survey: https://peerj.com/articles/cs-3773/). Benchmark annotation errors run 52.8% in BIRD Mini-Dev and 62.8% in Spider 2.0-Snow.
- How products expose operations:
    - **Notion:** structured rows-mode filters plus a separate read-only SQL mode (metered by plan).
    - **Airtable:** structured list plus a `filterByFormula` string written by the model.
    - **Excel Agent Mode / Gemini in Sheets / Claude in Excel:** native cell, range, formula, pivot and chart ops behind plan or diff approval.
    - **Quadratic:** model writes Python/JS/SQL/formula code cells (https://www.quadratichq.com/blog/streamline-spreadsheets-with-quadratics-ai-formula-generator).
    - **Julius:** writes Python/R in a sandbox.
    - **Hex:** Notebook Agent writes SQL/Python cells, grounded by a semantic layer (Context Studio) (https://www.tellius.com/resources/blog/best-ai-data-analysis-agents-in-2026-12-platforms-compared-for-nl-to-sql-autonomous-investigation-and-governance).
    - **Pattern:** code-writing agents run against a sandbox copy of the data, never the production database.
- **Takeaway:** for weaker models on single tables, use structured filter/sort/group args validated against the live schema. If raw SQL is ever offered, run it read-only against an in-memory copy of one table (DuckDB-WASM/SQLite), like Notion's SQL mode. Never run it against Postgres.

### 1.5 Formulas vs computed values

- MBABench (May 2026, finance spreadsheet tasks) — https://arxiv.org/html/2605.22664v2: agents including Claude for Excel and ChatGPT Excel "hard-coded" results instead of formulas. Values were usually correct, but the workbook was "unauditable". Best composite was 69.1/100 (Claude Web), falling to 53.4 on the hardest level.
- Derived-cell defect class (Aug 2026) — https://www.digitalapplied.com/blog/derived-numbers-agent-qa-pattern: agent tables state a formula and then print values that violate it (total ≠ sum, counts ≠ enumerations, inconsistent per-row application). Fix: route arithmetic through code, then "recompute every derived cell from its stated inputs before publish."
- CIFQA — https://arxiv.org/pdf/2608.26114: deterministic computation tools sharply cut arithmetic hallucination.
- jspreadsheet's agent tutorial (Aug 2026) recommends `write_formula` over static values so results stay live — https://jspreadsheet.com/blog/build-ai-spreadsheet-agent.
- **Takeaway:** the model should **never do arithmetic in tokens**. Totals and averages come from a server aggregate tool. Persisted derived values come from deterministic computed columns (column-level expression, column-name refs), not from model-written numbers. Full A1 cell formulas are not needed for CSV-like tables in v1.

### 1.6 Concrete design rules for a weak-model table tool suite

1. **Schema first.** `table_describe` returns name, row count, version, columns (name, type, select options, % empty, distinct count, min/max or top values, 2–3 example values), and linked entities. Target 200–600 tokens. Tool descriptions tell the model to call it first.
2. **Short stable row handles.** Use `r1…rN` per table: monotonic, never reused, and independent of sort or filter. Do not use UUIDs, A1 refs, or positional indexes. The server maps handles to UUIDs.
3. **Columns by display name.** Match case-insensitively. The server maps names to stable column IDs, so renames never rewrite rows. On a miss, return "Unknown column 'Stauts'. Did you mean 'Status'? Columns: …".
4. **Paged markdown reads.** Default 25 rows, max 100, column projection encouraged. The handle is always the first column. Long cells are truncated as `…(+340 chars)`. A footer says `showing 1–25 of 312 · next: cursor=…`. Wide rows (>12 cols) or long text switch to markdown-KV blocks.
5. **Inline only small tables.** If the table is about 50 rows × 8 cols or smaller, its full markdown can go straight into the focused-entity context. Otherwise send schema, first page, and stats.
6. **Structured query args.** `where: [{column, op: enum(eq, neq, contains, not_contains, gt, gte, lt, lte, is_empty, not_empty, in), value}]`, a single `match: all|any` (no nesting in v1), `sort: [{column, dir}]`. Text `contains` is case-insensitive by default. Values are coerced to column type, with clear errors.
7. **Server-side aggregates.** `table_aggregate(group_by?, metrics:[{fn: count|sum|avg|min|max|count_distinct, column}], where?)`. Prompt rule: "Never compute totals yourself; call table_aggregate."
8. **Sparse, keyed writes.** `table_write_rows(rows:[{row?: "r12", values:{Status:"Done"}}], insert_after?: "r7")`. No `row` means insert. Values are objects keyed by column name, never positional arrays. Max 100 rows per call. Return per-row OK/error, new handles, and coerced values.
9. **Harness-managed concurrency.** The server remembers which table version the agent last read in this chat turn. A write touching cells a human changed since then returns `conflict` with current values rather than overwriting. The model never handles version tokens (per OpenAI: don't make the model supply what you already have). Idempotency key per call, so retries don't duplicate inserts.
10. **Two-phase destructive ops.** Where-based bulk updates, deletes, column drops and lossy retypes return a preview (count + 5 before→after samples + `confirm_token`). Small non-destructive edits (≤20 rows) auto-apply. Everything goes into an op log with `batch_id`, so the UI can offer one-click "Undo agent change", like Claude in Excel and Excel Agent Mode.
11. **No retyping data.** CSV/TSV import goes through a tool that parses an uploaded asset or pasted text server-side. The model never copies hundreds of rows into tool args.
12. **Load table tools only when needed.** Expose the table tools when a table is focused or a skill is loaded, to stay under about 20 tools per turn.
13. **Actionable errors and truncation messages** that say what to call next.
14. **Highlight agent edits.** Every agent write is stamped `actor=agent` so the grid can highlight changed cells, building trust the way Claude in Excel does.

Suggested tool set (7): `table_describe`, `table_read_rows`, `table_aggregate`, `table_create` (with optional seed rows ≤100 and `link_to`), `table_write_rows`, `table_bulk_change` (where + set/delete, preview/confirm), `table_alter_columns` (add/rename/retype/remove/reorder; lossy ops need confirm). Optional later: `table_import` (asset → rows) and `table_sql` (read-only, sandboxed, strong models only).

**License traps:**

- **Handsontable:** proprietary, commercial use needs a paid key.
- **AG Grid:** the spreadsheet-feel features (range select + Excel paste) are Enterprise, so the free version quietly lacks the thing users expect.
- **HyperFormula:** GPLv3 (see §3).
- **RevoGrid / SvGrid / jspreadsheet:** MIT cores with paid upsells. Fine, but keep to core features.
- No non-commercial-only or GPL traps found in SVAR, Tabulator, TanStack, RevoGrid core, or SvGrid core.

**Recommendation:**

- **Desktop grid: RevoGrid core** via `@revolist/svelte-datagrid`, lazy-loaded on the table surface only (~105 KB gz). It is the only mature MIT option with Excel/Sheets range paste, autofill, range selection, row/col virtualization, row/col drag and CSS-variable theming in the free core. `--revo-grid-*` maps cleanly to Inkprint tokens, including dark.
- **Phone: a Svelte-native record-card list** (tap a row to open a sheet editor) rather than a grid. Spreadsheet grids on phones are poor whatever the library. This matches the existing phone-sheet pattern in BuildOS.
- Put both behind one `TableView` component so swapping later is cheap.
- **Fallback if the pure-Svelte look wins:** SVAR (56 KB, MIT, very Svelte-idiomatic). You would add a `paste` handler (Papa-parse TSV → rows) yourself and live without range selection.
- **Watch:** SvGrid. It has the right feature set in MIT and native runes, but it is about 4 months old.
- **Ambitious alternative:** a hand-rolled grid on TanStack Table v9 + Virtual, giving full Inkprint fidelity and "watch the agent fill the table" live-cell animation. Costs about 2–4 weeks.

**Recommendation:** **skip cell formulas in v1.**

- Ship typed values plus a server-side `table_aggregate` tool, and show column totals in a footer computed by the same code.
- In v1.5, add **computed columns**: one expression per column with column-name refs (`{Price} * {Qty}`, `IF({Status}="Done",1,0)`). Evaluate them with a tiny in-house parser (allow-listed AST, no `eval`) calling `@formulajs/formulajs` functions, run identically in browser and Node. This captures MBABench's auditability benefit without A1 refs and without GPL.
- Only consider HyperFormula (paid), IronCalc or Univer if users demand true spreadsheet formulas.

**CSV:**

- **Papa Parse 5.7.0** (MIT, 7 KB gz, 2026-08, ~20M dl/wk): browser + Node, header mode, delimiter auto-detect, streaming/worker, `unparse` for export. It also parses clipboard TSV (`delimiter: '\t'`).
- uDSV (MIT) benchmarks 2–5× faster but was last published 2025-07 (https://github.com/leeoniya/uDSV/tree/main/bench).
- csv-parse (MIT, 7.0.3) is Node-stream oriented.
- Benchmarks: https://leanylabs.com/blog/js-csv-parsers-benchmarks/ , https://github.com/dev-ahmadbilal/csv-parser-benchmarks
- **Export safety:** neutralize formula injection. Prefix `'` to cells starting with `=`, `+`, `-`, `@`, tab or CR (OWASP: https://owasp.org/www-community/attacks/CSV_Injection , WSTG https://owasp.org/www-project-web-security-testing-guide/latest/4-Web_Application_Security_Testing/07-Input_Validation_Testing/21-Testing_for_CSV_Injection). This matters more when agents write cell text.

**Indexing facts** (https://www.postgresql.org/docs/current/datatype-json.html):

- GIN `jsonb_ops` supports `? ?| ?& @> @? @@`. `jsonb_path_ops` supports only `@> @? @@` and is smaller and faster.
- Range or sort on `cells->>'c_x'` needs an expression B-tree, i.e. DDL per column. Avoid it. At ≤10k rows per table, a `(table_id)` index + in-table scan + typed cast in `ORDER BY` is fast enough.

**Row ordering:**

- Fractional keys with `fractional-indexing` 4.0.0 (CC0, rocicorp, 3.6M dl/wk).
- **Landmine:** the column and index must use `COLLATE "C"`. Default `en_US.utf8` sorts base62 keys differently from JS, so order breaks only in prod. Sources: https://www.solberg.is/fractional-indexing-gotcha (2026-01-21), https://github.com/payloadcms/payload/issues/12397
- The agent never sees sort keys; it says `insert_after: "r7"`.

**Limits for reference:**

- Airtable: 1k records/base on Free, 50k on Team, 125k on Business, 500k on Enterprise Scale (https://infolobby.com/blog/airtable-record-limits-when-to-move-to-a-database).
- Google Sheets: 10M cells per workbook (https://rowzero.com/blog/google-sheets-limits).
- Suggested v1 cap: 10k rows × 50 columns per table, cell ≤ 10 KB, soft-warn at 5k rows.

**Recommended schema sketch** (to be written as a new migration later, with `db:rehearse` and RLS via project membership like other onto entities):

- `onto_tables`: id, project_id, title, description, `columns jsonb` ([{id:'c_k3f9', name, type: text|number|date|select|multiselect|checkbox|url|person|link, options, width, position, computed_expr?}]), `next_row_no int`, `row_count`, `version bigint`, created_by, timestamps, deleted_at.
- `onto_table_rows`: id uuid, table_id, `row_no int` (the agent handle; unique per table, never reused), `sort_key text COLLATE "C"`, `cells jsonb` (keyed by column ID, so renames are free), `version int`, `updated_by_actor` ('user'|'agent'), `updated_by`, timestamps, deleted_at (soft delete for undo). Indexes: unique (table_id, row_no); (table_id, sort_key) WHERE deleted_at IS NULL; optional GIN (cells jsonb_path_ops).
- `onto_table_ops`: id, table_id, batch_id, actor, op (insert/update/delete/alter), row_ids, `before jsonb`, `after jsonb`, created_at. Powers undo, agent attribution, highlights and an activity feed.
- Links to tasks and docs through existing `onto_edges` (`src_kind = 'table'`); optionally a row-level link (`table_row`) later.
- Writes go through one RPC per batch (lock-first on the table row, matching the tasker-105 lock-order convention). The RPC bumps `onto_tables.version`, writes the op log, and returns per-row results. Realtime subscribes to `onto_table_rows` filtered by `table_id` so agent edits appear live in the grid.
- New functions are server-only by default; add `GRANT EXECUTE … TO authenticated` only where the browser calls them, and check `auth.uid()` in any SECURITY DEFINER function.

## 5. Open questions / forks for DJ

1. Feel: **Airtable-lite** (typed columns, select chips, linked rows, cards on phone) or **Sheets-lite** (free cells, A1 feel, formulas)? The research strongly favors Airtable-lite for agent reliability and for linking to tasks and docs.
2. Grid look: RevoGrid's spreadsheet feel (Excel paste, autofill) vs SVAR's more native-Svelte look without range paste. Or the ambitious hand-rolled Inkprint grid with live agent-cell animation.
3. Formulas: OK to ship v1 without formulas, using totals footer + agent aggregates, with computed columns in v1.5?
4. Paid escape hatch: if true Excel formulas are ever required, HyperFormula costs about $1.5k/yr minimum. IronCalc and Univer are the permissive alternatives.
