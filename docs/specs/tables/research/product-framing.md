# Tables in BuildOS: external product research and framing

Date: 2026-10-04. Scope: how docs/notes/thinking tools added structured tables, the AI-native table category, naming/framing, and the narrowest wedge for solo builders/founders/creators. All claims cite a URL. Where a source is a vendor blog or a secondary review site, that is noted.

---

## 0. The one insight to keep central

The single most useful sentence in this research comes from a 2026 post on why teams leave Notion:

> "Notion is not a tool, it is a construction kit, and the bill arrives as maintenance." ... "This is not a failure of discipline, it is the predictable consequence of a tool that must be designed before it can be used." ([storyflow.so](https://storyflow.so/blog/notion-maintenance-tax-and-what-to-move-to-2026))

Every database-in-a-doc product pays this tax: the user has to design the schema, views, and relations before getting value, then maintain them as reality changes. The AI-native products (Clay, Hebbia, Elicit, Notion 3.0 agent, Airtable Omni, Excel Agent Mode) all attack exactly that cost. They let the user say what they want and have the system design the grid, fill it, and keep it current.

**For BuildOS, the relief is that you never design the table. You say what you're keeping track of, and the agent builds it, fills it, ties it to the work, and keeps it fresh.** That fits "turn messy thinking into structured work" literally: a table is structured work.

### 1.2 Per-tool notes with sources

**Notion**

- Rows are pages: "database rows can open to new Notion pages where you can store important information related to the topic of the row." Notion recommends switching from a simple table to a database "anytime you are wanting to filter or sort through said information." ([Notion help: simple tables vs databases](https://www.notion.com/help/guides/simple-tables-vs-databases))
- In Sept 2025 Notion added a layer: a database is now a container of one or more **data sources**, each with its own schema, and each parents pages. The API change "is not backwards-compatible." ([Notion upgrade guide 2025-09-03](https://developers.notion.com/docs/upgrade-guide-2025-09-03), [Thomas Frank](https://thomasjfrank.com/notion-databases-can-now-have-multiple-data-sources/)) The data model keeps getting more complex.
- Setup tax: "every database starts from zero - you create a table, decide what kind of database it is, add data and properties, build views, then tweak everything again and again as new data keeps flowing in." "each database is its own little island with its own rules." ([XDA](https://www.xda-developers.com/notion-databases-great-but-obsidian-bases-better/))
- Maintenance decay: "A property stops being filled in. A view starts showing stale rows... Nine months later the workspace contains three overlapping systems, two of which are abandoned." Teams leave because of decay more than performance: "a tool that must be designed before it can be used requires someone to keep designing it, and that person is rarely funded." ([storyflow.so](https://storyflow.so/blog/notion-maintenance-tax-and-what-to-move-to-2026))
- The system-building trap: "you need a projects database. And projects have areas, so you need an areas database. You should link them with relations, create different views, add a dashboard..." The critic then switched to a text file "and started finishing things." ([ilikekillnerds, Jan 2026](https://ilikekillnerds.com/2026/01/20/notion-is-where-productivity-goes-to-die/))
- Performance (secondary sources, treat numbers as directional): slowdowns start "when databases exceed a few thousand rows... or when relations and rollups create computational chains." ([Fabric](https://fabric.so/blog/why-notion-is-slow), [latwy](https://latwy.co/knowledge-base/why-is-notion-slow-with-large-databases)). Capterra/AWS reviewers: mastering databases, relations, formulas "required extra time and effort"; "Notion AI struggles with debugging tables with relations and rollups." ([Capterra](https://www.capterra.com/p/186596/Notion/reviews/?page=14))
- AI: the Notion 3.0 agent (Sept 2025) builds databases from a prompt, for example "Create a marketing campaign database... Include columns for owner, due date, and status. Add timeline and board views." ([Notion 3.0](https://www.notion.com/blog/introducing-notion-3-0), [Reworked](https://www.reworked.co/collaboration-productivity/notion-30-introduces-ai-agents-for-task-automation/)). Autofill comes in two kinds. Basic autofill (summaries, tagging, translation) "only uses content in the specific row or page." Custom Agent autofill uses workspace and web search, can update multiple properties, runs on schedules, and costs credits. ([Notion autofill help](https://www.notion.com/help/autofill)). Notion 3.4 (Apr 2026) made Custom Agents 35–50% cheaper. ([AlternativeTo](https://alternativeto.net/news/2026/4/notion-3-4-adds-ai-autofill-and-cheaper-custom-agents-for-teams/))

**Coda / Superhuman Docs**

- Base tables plus views: "A view is essentially a connected 'mirror' of that base table." The canvas column puts a page inside a row. ([Coda help: canvas column](https://help.coda.io/hc/en-us/articles/39555806187917-Canvas-column-type), [Coda tables overview](https://help.coda.io/hc/en-us/articles/39555768266893-Overview-Tables))
- AI column: "You can add AI to any column type... and @ reference other data within the row. As more rows are added, AI column will auto-populate." ([Zapier on Coda AI](https://zapier.com/blog/how-to-use-coda-ai/), [Coda AI features](https://help.coda.io/hc/en-us/articles/39555802361613-Coda-AI-features))
- Performance: "Coda docs with more than a thousand rows, several linked tables, and complex formulas load slowly"; teams building "operating systems" "hit this wall around 50-100 connected tables." ([Capterra](https://www.capterra.com/p/193164/Coda/reviews/), [Superhuman community thread](https://connect.superhuman.com/t/like-the-concept-but-performance-is-a-showstopper/6881), [Coda: improve doc performance](https://help.coda.io/hc/en-us/articles/39555858659853-Overview-Improve-doc-performance))
- Corporate: Grammarly acquired Coda (Dec 2024). Grammarly rebranded to Superhuman (Oct 2025), and Coda became Superhuman Docs. ([Coda blog](https://coda.io/blog/about-coda/grammarly-acquires-coda), [Superhuman help](https://help.superhuman.com/hc/en-us/articles/46210093285773-What-s-changing-Coda-becomes-Superhuman-Docs)). July 2026: "new table pages... a full-screen page type built for structured data." ([Coda what's new](https://coda.io/product/whats-new)). Even the docs-as-apps pioneer ended up giving tables their own page type.

**Airtable**

- Relaunched June 24, 2025 as an "AI-native app platform", which the CEO called a "refounding moment." **Omni** builds tables, interfaces, and automations from conversation. **Field Agents** are "AI-powered researchers, analysts, and content creators" that run per record (enrich leads, extract from transcripts, triage feedback, web research). ([Reworked](https://www.reworked.co/digital-workplace/airtable-relaunches-as-ai-native-app-platform-with-omni/), [Airtable community announcement](https://community.airtable.com/announcements-6/introducing-the-ai-native-airtable-45645), [Airtable AI](https://www.airtable.com/platform/ai))
- Hands-on review (June 2025): import and automations worked ("surprised it worked on the first try"), but "the chatbot is a bit buggy... It forgets to respond, ignores instructions and sometimes just errors out." The reviewer wanted it to say "if something is doable or not" and to "fail more gracefully." Score 5.75/9. ([rnikhil](https://rnikhil.com/2025/06/28/airtable-omni-review))
- Pricing pain: the per-seat model; the free plan is capped at 1,000 records; Team is capped at 50k records per base, and crossing it forces a 125% per-seat jump. ([eesel](https://www.eesel.ai/blog/airtable-pricing), [servalian](https://servalian.com/blog/airtable-record-limits))

**Obsidian Bases (1.9, 2025)**

- "A core plugin that lets you create database-like views of your notes." "All the data in Obsidian Bases is stored in your local Markdown files and their properties." It lives in a `.base` file or is embedded in a note as a code block. Views: table, list, cards, kanban, map. Formulas compute derived properties. ([Obsidian help: Bases](https://obsidian.md/help/bases), [Views](https://obsidian.md/help/bases/views), [1.9.0 changelog](https://obsidian.md/changelog/2025-05-21-desktop-v1.9.0/))
- Launched with **table only**. The early reviewer's limits: table-only, no images, no inline properties. ([Practical PKM](https://practicalpkm.com/bases-plugin-overview/)). An API for custom views followed in 1.10. ([Obsidian Oct 2025](https://obsidian.md/blog/2025-obsidian-october/))
- Reception: "It's not meant to be as 'kitchen sink' comprehensive yet, but it's a like 90% replacement and it's a ton faster and more responsive." ([HN](https://news.ycombinator.com/item?id=44059926), [HN thread](https://news.ycombinator.com/item?id=44945532)). XDA: Bases "turns your existing vault of notes into dynamic and structured views without forcing you to build a siloed database from scratch." ([XDA](https://www.xda-developers.com/notion-databases-great-but-obsidian-bases-better/), [XDA 2](https://www.xda-developers.com/obsidians-new-bases-feature-replacing-notion-workflow-for-good/))
- **Lesson for BuildOS:** the best-received launch of the year was a _view over things that already exist_, shipped with one view type. BuildOS already has typed entities (tasks, docs, goals, milestones). A "table view of my tasks with an effort column" is the Bases move.

**Tana**

- "Supertags turn a node into a typed object with a template of fields. All nodes with the same supertag form a collection you can search, filter, and view as a table." ([Tana docs: supertags](https://tana.inc/docs/supertags), [fields](https://tana.inc/docs/fields), [views](https://outliner.tana.inc/learn/features/views))
- AI: "AI-enhanced" fields, and voice memos that "transcribe the recording and fill in fields based on your supertag configuration." ([Tana AI](https://outliner.tana.inc/learn/features/tana-ai), [voice memos](https://outliner.tana.inc/learn/features/mobile-voice-memos)). This is the closest existing analog to BuildOS's messy voice → structured fields.
- Cost: "Tana rewards power users with the steepest learning curve in note-taking"; new users "spend days or weeks understanding how to effectively use supertags and queries." ([Saner review](https://blog.saner.ai/tana-reviews/), [aishortcutlab](https://aishortcutlab.com/tools/tana/review))

**Anytype**

- Sets "use queries which automatically fetch objects", while Collections "depend on linking the objects manually." ([Anytype community](https://community.anytype.io/t/collection-vs-sets/10335))
- Anytype's own admission: "our software has a learning curve, compounded by unique terms in our information architecture and significant complexity." The fix is formats: "a Page works as a block-based editor, a List functions like a database." "The greatest products are simple but robust." ([Anytype 2025 plans](https://blog.anytype.io/our-journey-and-plans-for-2025/)). A review claims the app "loses 90% of the new users" (unverified, secondary). ([thebusinessdive](https://thebusinessdive.com/anytype-review))
- **Lesson:** a team that started with invented nouns (Sets, Collections, Relations) retreated to "List." Plain nouns win.

**Capacities**

- Two tiers. (1) Object types with properties, with table view as "the most detailed of our data views." (2) **Simple tables**: "visually structured information without the need for a full database functionality," created with `/table`. Cells take object links through `@` or `[[ ]]`, there are basic formulas (SUM, AVERAGE...), and tables export to CSV. Pro users can promote a table to a **table object** that gets "all the perks of being an object... use them in any other object." ([Capacities: tables](https://docs.capacities.io/reference/tables), [table objects](https://docs.capacities.io/reference/basic-types/table-object), [views](https://docs.capacities.io/reference/views))
- Cost: "the object system requires you to make a structural decision for every piece of content." ([Saner](https://www.saner.ai/blogs/capacities-review))
- **Lesson:** "simple table in a doc → promote to a named, linkable object" is a clean ladder, and it is close to what DJ described (CSV-like, linkable to docs/tasks).

**Craft**

- "You can embed a Collection directly into any document, with no overhead required for managing a separate database." ([Craft blog](https://www.craft.do/blog/introducing-collections)). Up to 20 custom fields plus title; field types include relations; table and gallery views; filter, sort, group; any row can open as a page. ([Craft help](https://support.craft.do/hc/en-us/articles/16446209188380-Craft-Collections))
- Reviews: "Collections are not true relational databases"; good "for light tracking." ([2sync](https://2sync.com/blog/craft-vs-notion), [atlasworkspace](https://www.atlasworkspace.ai/blog/notion-vs-craft))

**Linear: why no tables or custom fields**

- "We support labels and label groups for organization, but believe that the bloat of endless custom fields leads to more harm than good. As it turns out, Oscar didn't miss them at all." Oscar's Jira had hit the custom-field limit. Pete Zalewski: "If you're offered custom fields you're going to have the urge to use them. They coagulate as a workflow that doesn't suit anyone." ([Linear: Oscar](https://linear.app/customers/oscar), [Gergely Orosz](https://x.com/GergelyOrosz/status/2024259505232462143))
- **Lesson:** opinionated, fixed structure beats configurable structure for focus. Linear gets "trackability" from a fixed schema plus labels, not from a grid.

**Basecamp**

- A to-do "is just a name, an assignee, and a due date"; there is "no native grid or table-based interface." ([getassistant](https://getassistant.io/blog/whats-new-in-basecamp-5/), [productowl](https://www.productowl.io/task-management/basecamp)). Instead, 37signals ships purpose-built trackers. Timesheet: "track time directly in Basecamp — no spreadsheets required," with CSV export. ([37signals](https://updates.37signals.com/post/new-in-basecamp-timesheet))
- **Lesson:** "no spreadsheets required" is a relief framing that already works. Absorb the side spreadsheet into the place the work lives.

**Spreadsheet incumbents moving toward "tables"**

- Google Sheets "Convert to table" (May 2024) adds typed columns (dropdown, date, checkbox, smart chips) and templates such as "Project tracker, Event planning, Inventory." ([Workspace Updates](https://workspaceupdates.googleblog.com/2024/05/tables-in-google-sheets.html), [Google help](https://support.google.com/docs/answer/14239833?hl=en))
- Microsoft's own framing: "Excel is for calculation while Lists is for tracking." Lists is "a shared spreadsheet with guardrails." ([Vantage365](https://training.vantage365.com/microsoft-lists/), [SharePoint Maven](https://sharepointmaven.com/lists-vs-excel/))

### 2.2 The interaction patterns (named) and which to steal

1. **"Say it, get the table" (chat → table appears).** Notion 3.0 agent, Airtable Omni, Clay Sculptor, Gemini "Help me organize," Shortcut, Excel Agent Mode. _Steal: yes, as the main way tables get created. It removes design-before-use._
2. **"Column = question" (an AI column runs a prompt per row).** Clay Claygent, Hebbia, Elicit, Airtable field agents, Coda AI column, Notion autofill, `=COPILOT()`, `=AI()`. _Steal: yes, for research-ish columns ("find their LinkedIn," "pricing tier," "does this tool have an API?")._
3. **"Table as research output, with receipts."** Elicit (quotes and reasoning per cell), Hebbia (click a cell for its source), Claude for Excel (cell citations). _Steal: yes. Every AI-filled cell carries its source. BuildOS already values cited evidence and write receipts (tasker 96)._
4. **"Rows are your documents."** Hebbia and Elicit use docs/papers as rows; Obsidian Bases uses notes as rows. _Steal: as a view over BuildOS entities (tasks, docs) rather than a separate store._
5. **"Agent edits the grid safely."** Claude for Excel (preserve relationships, warn before overwrite, confirm risky operations), Excel Agent Mode (plan → execute → verify → summary). _Steal: diff plus confirm for bulk edits; a changes summary in chat._
6. **"Capture fills fields."** Tana voice memo → supertag fields. _Steal: BuildOS's brain-dump flow can append rows to an existing table ("talked to 3 leads today" → 3 row updates)._
7. **"Clarify before building."** Shortcut asks questions first. _Steal: one short clarifying turn when columns are ambiguous, matching DJ's "interviews ≤3 Qs" pattern._

### 2.3 What users love and hate

- **Love:** no formulas or setup; one instruction applied to every row; output in a familiar grid ("analysts live in spreadsheets, not chat windows"); traceability (click a cell, see the source); real time savings ("came back to a P&L").
- **Hate or fear:** cost surprises when re-runs bill every row (Clay); chat builders that fail silently or ignore instructions (Omni review); research narrated as prose when the answer is really a table ("questions whose answer is fundamentally a table are narrated instead," [aitoolradar](https://aitoolradar.io/blog/deep-research-showdown)); confident-looking output built on missing data (Shortcut); accuracy ceilings (Agent Mode 57.2%); prompt-injection risk from external files ([Claude docs](https://claude.com/docs/office-agents/excel)).

## 3. Naming and framing

### 3.1 What others call it

| Name                | Who                                                           | Connotation                                                                  | Fit for BuildOS                                               |
| ------------------- | ------------------------------------------------------------- | ---------------------------------------------------------------------------- | ------------------------------------------------------------- |

### 3.2 Three framing options

1. **"Keep track of anything, without building a system."** (frame: Trackers) You say what you're keeping track of (leads, posts, hours, options) and BuildOS builds the table, fills what it can, and keeps it tied to the work. _Relief: an end to setup and upkeep. Speaks directly to the Notion-tax refugee._
2. **"Ask a messy question. Get a table you can act on."** (frame: research → table) Comparisons and research land as sortable tables with sources on every cell, and any row becomes a task or a doc in one move. _Relief: no more copying findings out of chat into a spreadsheet. Shows the AI without leading with "AI."_
3. **"No more spreadsheet on the side."** (frame: absorb the side-sheet, Basecamp-style) The outreach list, content calendar, and budget you keep in a stray Google Sheet now live next to the project they're about, connected to its tasks and docs. _Relief: one place, nothing to reconcile._

**Recommendation:** use **"Table"** as the plain noun in the UI (a format, not a system), and market with **option 1** ("keep track of anything without building a system") as the umbrella, with **option 2** as the hero demo because it's the most shareable "wow" moment. Use option 3 in onboarding and empty states ("Have a spreadsheet for this? Paste it."). Entry points should be framed as jobs ("Track outreach," "Compare options," "Plan content," "Log time"), the Basecamp purpose-built pattern on top of one generic primitive. Never use the words "database," "schema," "property," or "relation" in the UI.

## 4. The narrowest wedge (3–5 use cases)

Evidence for demand:

- Notion template sales: "Four categories carry roughly two-thirds of paid sales by volume: productivity systems, personal finance, content calendars, and lightweight CRMs." CRMs have the "highest average order value." (SendOwl, July 2026; vendor blog, no stated methodology. [SendOwl](https://www.sendowl.com/blog/tips-and-advice/best-selling-notion-template-categories))
- Outreach: "For solo founders... or anyone sending fewer than 200 pitches a month, a free spreadsheet does the job with fewer clicks than a paid CRM." Typical columns: name, contact, last contact date, stage, follow-up date, status, notes. ([bouncecheck](https://bouncecheck.email/blog/google-sheets-email-outreach-tracker-template))
- Content calendars: one row per post (date, platform, format, hook, status, link, performance). ([bettersheets](https://bettersheets.co/blog/social-media-scheduler-google-sheets))
- Time/effort: Basecamp shipped Timesheet with "no spreadsheets required" ([37signals](https://updates.37signals.com/post/new-in-basecamp-timesheet)).
- Research comparison: the core use of Elicit and Hebbia; Clay's whole business is the per-row research column.

**Ranked wedge for BuildOS (solo founder/builder/creator):**

1. **Outreach / people pipeline** (leads, creators, investors, clients). Columns: name, link, stage, last touch, next step. _Why first:_ the most natural row → task link (follow-ups), the highest-value AI column ("research this person/company" in the Clay pattern, lite), and DJ himself runs outreach (dogfood).
2. **Research comparison ("options table").** Rows are options (tools, vendors, competitors, venues); columns are criteria, with sourced cells. Links to a decision doc. _Why:_ this is the "research → table → link" flow DJ described, and the hero demo.
3. **Content pipeline / calendar.** Rows are pieces, with status, date, and channel. Each row links to its draft doc. _Why:_ creators already keep this in a sheet, and BuildOS already holds the drafts.
4. **Effort / time log.** Hours or effort per task or project. _Design fork:_ is this a column on tasks (a Bases-style view over existing tasks) or a separate log table? The view approach is cheaper and avoids double entry.
5. **Simple budget / expense list** (optional fifth). High demand, but it pulls toward formulas. Keep it to sum/count/avg column totals only.

Leave out of v1: inventory, habit trackers, financial models, anything relational.

## 5. "Don't become Notion" guardrails

1. **No design-before-use.** Tables are created by describing them (chat, brain dump, or paste/CSV). The agent proposes columns; the user never faces an empty "add property" screen. (Cure for the storyflow "construction kit" tax.)
2. **Tables belong to projects and attach to work.** A table lives in a project's doc tree like a document and links to tasks and docs through BuildOS's existing link edges. **No relations or rollups between tables** in v1. Relations and rollups are where Notion's complexity and slowness concentrate.
3. **A small, fixed set of column types**: text, number, date, status/select, checkbox, URL, and "link to BuildOS item." No user formulas, only column summaries (sum, count, avg). (Linear's lesson: offered fields "coagulate.")
4. **Two or three views, maximum**: table, board (grouped by status), and perhaps calendar (by date). Obsidian shipped table-only and won roughly 90% of the value.
5. **A row is not a page by default.** A row can be promoted to a task or doc in one move (the Craft/Capacities ladder), but you don't get Notion's "every row is a page" weight.
6. **The agent does the upkeep.** It fills empty cells, flags stale rows, and appends rows from brain dumps. Bulk or overwriting edits show a diff and ask for confirmation (Claude for Excel's overwrite protection). This is the actual product: tables that stay current without an owner.
7. **Every AI-filled cell has a receipt** (source link or quote) and looks visually distinct from human-entered cells (Elicit/Hebbia). Re-runs touch only changed or empty rows, never the whole table (Clay credit lesson).
8. **Size ceiling: hundreds of rows, not 50k.** CSV import and export is the escape hatch (Basecamp, Capacities, and Elicit all export CSV). Past the ceiling, point to Sheets instead of building a spreadsheet engine.
9. **Plain nouns only.** Call it a Table. Never show "database," "schema," "property," "relation," "base," "set," or "collection."

---

## 6. Lean vs ambitious (for DJ to pick)

- **Lean:** a Table as a new document-like entity inside a project (CSV-backed rows, fixed column types, table plus board view), created by chat or paste, rows linkable to tasks/docs, and an agent tool suite (create_table, add_rows, update_cells, add_column, link_row). Reuses existing edges and the doc tree.
- **Ambitious:** everything in lean, plus **AI columns with sourced cells** ("column = question," run per row, receipts per cell, re-run only stale rows) and **views over BuildOS's own entities** (an Obsidian Bases-style "table of my tasks with effort/owner/due," and a "table of docs in this folder"), plus **brain-dump → row updates** (Tana-style capture fills fields). That combination is something nobody in the solo-founder tier has: research → table → tasks in one environment, kept fresh by an agent.
