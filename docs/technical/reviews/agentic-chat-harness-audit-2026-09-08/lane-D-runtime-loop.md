# Lane D — Shared runtime loop modules (`packages/agentic-chat-runtime`)

Audit date: 2026-09-09T02Z. Tree: working tree on top of `6d70b36e1` (main). Read-only.

Scope: `packages/agentic-chat-runtime/src/loop/*`, `src/supervisor/*`, `src/{contracts,ports,last-turn-context,lifecycle-observability,worker-tool-policy}.ts`, the package `exports` map, and the web shims under `apps/web/src/lib/services/agentic-chat-v2/turn-supervisor/` plus the three web wrappers `turn-contract.ts` / `turn-intent.ts` / `turn-outcome.ts`.

Question answered: which of this code is load-bearing for the Railway worker today, which is a leftover of the deleted web engine, and where the load-bearing part fights a cheap acting model.

Evidence files (this folder, `evidence/`):

- `lane-D-import-graph.json` — per-exported-symbol importer counts (319 symbols) and bucket; generated by `lane-D-graph.mjs` (grep -rw across `apps/worker/src`, `apps/web/src`, `packages`, non-test).
- `lane-D-contract-rejections.json` — the 9 production turns (of 24 contract turns, 2026-09-04..09-08) whose `declare_turn_contract` was rejected by validation, with per-turn pass/token/latency and the averages against the 15 clean contract turns. Source: `lane-h-turns.json`.

## 1. How this subsystem runs today (map)

The worker's turn loop lives in `apps/worker/src/workers/agentic-chat/provider/turn-provider.ts` (1,853 lines) and `turn-executor.ts` (3,971 lines). Those two files are the only place a turn is orchestrated; `@buildos/agentic-chat-runtime/loop` supplies pure helpers that they call. There are 21 import sites of `/loop` in `apps/worker/src` and 19 in `apps/web/src`; the worker never imports the package root or `/supervisor`; the web imports `/supervisor` only from six 2–13 line shim files that nothing else imports.

Per acting pass the worker calls, in order: `parseToolArguments` (model JSON repair), `validateToolCalls` (schema/UUID/update/contract validation, `tool-validation.ts:131`) plus the worker's own `validateContractEffectFields` (`provider/contract-fields.ts:17`) and project-shell rules (`provider/validation.ts:150-243`), then, on a read round, `buildRoundToolPattern` → `ContextGatheringLedger.observeToolRound` → `selectReadLoopRepairEscalation` (`turn-provider.ts:811, 995-1027`), and on a write round `buildWriteLedger` → `bindTurnContractLabels` → `resolveTurnContractOutcome` (`turn-provider.ts:354, 379-417`). Tool results go back to the model through `stripToolDiscoveryHintsFromPayload` (`provider/feedback.ts:125`) and then `buildToolPayloadForModel` (`provider/request-builders.ts:262`), which strips hints again, compacts known payload shapes, and prepends a 157-character security notice to every result. At terminal time `terminalTextIntegrity.ts:29` recomputes the contract from executions (`reviewedTurnContract.ts`), runs `enforceMutationOutcomeIntegrity` (71 regexes over the answer) and `applyFinalizationGuard` (rewrites or synthesizes the answer), then `sanitizeAssistantFinalText` runs twice (once inside the guard, once in `turn-provider.ts:1802`). After finalization two post-turn side effects run: `captureResearch` and `captureStatedFuture` (`turn-executor.ts:822-827`).

Pending-contract carry-forward is computed twice with different semantics: once in TypeScript for the terminal disclosure (`resolveTurnContractOutcome`) and once in SQL by trigger `trg_chat_turn_runs_terminal_pending_contract` (`supabase/migrations/20260814011000…:204`), which is what actually writes `fastchat_pending_turn_contract` into session metadata; web admission reads it back with `readFastChatPendingTurnContract` (`turn-preparation.ts:123`) and renders it via `buildPendingTurnContractSystemMessage` (`worker-turn-preparation.server.ts:705`). Web admission also still runs the retired lexical intent classifier (`resolveFastChatTurnIntent`, always empty) and two `chat_turn_checkpoints` queries for a table nothing has written since the supervisor was deleted on 09-02.

## 5. Findings (structure and reachability)

### 5.1 Web admission still runs the retired lexical intent classifier and two dead checkpoint queries per turn

- `turn-intent.ts:68-76` `resolveFastChatTurnIntent` returns `emptyIntent()` unconditionally; `:115-124` `buildFastChatPendingTurnIntent` returns `null`; `:143-151` return `false`/`null`. The only reader of the result is `worker-turn-preparation.server.ts:657` (`turnIntent?.requiresWrite === true`, always false). The migrations that nulled `fastchat_pending_turn_intent` date from 08-13/08-14; any legacy pending intent expired long ago (`:95-98` expiry check).
- `worker-turn-preparation.server.ts:391-398` → `loadWorkerResumeCheckpoint` (`:993-1012`) → RPC `recover_agentic_chat_resume_checkpoints` + `chat_turn_checkpoints` select, on every turn without a prepared-admission hit (50/55 production turns). Nothing writes the table (§2.3). `request-builders.ts:174-177` still injects `resumeCheckpoint.resumeMessage` if present.

### 5.2 `tool-arguments.ts`: 511 of 759 lines have no production caller

Live: `parseToolArguments` (`:27-63`) and its recovery helpers (`:472-672`) — code-fence stripping, nested-string decoding, balanced-segment extraction and merging of concatenated JSON objects. This is exactly the tolerance a weak model needs and it is used by every validator and the ledger. Dead or test-only: `normalizeToolCallDefaults` (`:64-245`, normalizes `tool_schema`/`skill_load`/`skill_reference_load`, none worker-executable), `stampProjectCreateGenerationModel` (`:246-292`), `backfillCommissionedDocumentUpdateContent` (`:293-314`), `inspectToolArgumentAnomaly`/`logToolArgumentAnomaly` (`:315-372`), `sanitizeToolCallsForReplay` + redaction (`:384-471`), `buildGatewayFallbackArgs` (`:695-760`).

### 5.3 `tool-payload-compaction.ts`: ≈550 lines compact payloads of tools the worker cannot call

`buildToolPayloadForModel` (`:168-217`) routes 13 tool names (`domain_search`, `domain_load`, `outcome_card_*`, `work_capability_*`, `tool_schema`, `tool_search`, `skill_search`, `resource_*`, `skill_load`, `skill_reference_load`) to `compactGatewayMetaPayload` (`:350-752`, 403 lines) and skill helpers (`:218-343`). None of the 13 is in the worker's executable set: `worker-tool-policy.ts:84-95` omits the discovery tools and `tools/shared-read-dispatch.ts:47-107` (the 45 executable reads) contains none of them. Also: `stripToolDiscoveryHintsFromPayload` runs twice per read result (`feedback.ts:125` without a callable set, then `:191` inside `buildToolPayloadForModel` with one); and `addToolResultSecurityNotice` (`:238-260`) prepends a 157-character notice + two metadata keys (≈55 tokens) to every tool result, replayed on every later pass of the turn (production: 246 executions, mean 5.6 passes per turn).

### 5.4 `tool-validation.ts`: duplicated validators and a retired project shape validated at three layers

- `validateUpdateToolArgs` (`:396-430`, keyed by `update_onto_*` name) and `validateCanonicalUpdateArgs` (`:600-636`, keyed by `onto.*.update` op) check the same `${entity}_id` UUID and same "at least one field" rule; both run for every update call because the registry maps name→op. `validateUuidArgs` (`:437-460`) and the loop in `validateDirectOpArgs` (`:534-546`) duplicate the UUID check. `applyExactOpDiscoveryExecutionGuards` + `extractExactGatewayDiscoveryOp` (`:462-520`) only act on `tool_schema`.
- `create_onto_project`: `validateProjectCreateArgs` (`project-create-args.ts:389-403`) rejects a missing `entities` or `relationships` array; the worker adapter requires both to be present **and empty** (`createOntoProjectMutationAdapter.ts:192-203`); the tool description tells the model "Pass empty entities and relationships arrays" (`mutationToolCatalog.ts:894-895`) and the JSON schema marks them required (`:895`). The worker shell cannot use either (`EXPECTED_COUNTS` all zero except one document, `:59-70`). A cheap model that omits `relationships: []` gets a validation rejection and a repair pass for a field that carries no information.

### 5.5 Two read-saturation ladders per read round

`turn-provider.ts:995-1027` calls `ContextGatheringLedger.observeToolRound` (novelty/repeated-search ladder, 477 lines, own system message at `context-gathering-ledger.ts:283-315`) and then `selectReadLoopRepairEscalation` (count ladder, `read-loop-escalation.ts:24-38`, own system message via `buildReadLoopRepairInstruction`), merging by `readLoopRepairRank = max(...)`. Both can append an instruction in the same round. The `roundsRemaining <= 2` branch (`read-loop-escalation.ts:29`, `context-gathering-ledger.ts:191, 214`) is unreachable: `maxProviderRounds` defaults to 16 (`turn-executor.ts:117`, `config.ts:127`) but `MAX_PROVIDER_PASSES_PER_TURN = 12` (`turn-provider.ts:175`) ends the turn first. Production round distribution tops out at 9.

### 5.6 TypeScript and SQL compute the pending contract differently

The SQL trigger's normalizer (`20260814011000_agentic_chat_turn_contract_worker_hardening.sql:14-126`) keeps only `id, action, entityKind, targetIds, requiredFields, minimumSuccessfulEffects, description` — it drops `changes`, `label`, `parent_label`, `src_label`, `dst_label` — and floors `minimum := GREATEST(minimum, targets)` (`:108-113`), which the TypeScript resolver deliberately does not (`turn-contract.ts:1534-1540`, "an explicitly reviewed lower minimum permits a bounded partial outcome"). No later migration adds label or change support. Consequence: a carried-forward `move` loses its destination constraint and a carried-forward scalar change (`priority=1`) degrades to "field written". The TypeScript builder that handles these cases (`buildFastChatPendingTurnContract`, `:806-851`) is never called. Frequency: 2 of 55 turns ended `mutation_unfulfilled`, so the carry-forward path serves ≈4% of turns.

### 5.7 Cheap-model traps in load-bearing validators

- `validateExplicitProjectCreateName` (`provider/validation.ts:104-141`) extracts a name from the user's message by regex and compares with `canonicalDisplayName` (`:139-141`), which is case-sensitive: "create a project called my novel" → model names it "My Novel" → rejected ("must preserve that exact name") → repair pass. No production hit in artifacts; the trap is structural.
- `classifyReceiptGroundedAssistantDisposition` (`repair-instructions.ts:799-808`) withholds terminal prose and forces a gate pass (`turn-provider.ts:620-641`) when it matches `MUTATION_SUCCESS_CLAIM_PATTERNS` (`:1109-1119`) — including `/\b(?:i|we)(?:'ve| have)?\s+(?:…|moved|…|set)\b/`, which matches "I've set out the key points" and "we've moved on to" — or `UNRESOLVED_CHOICE_QUESTION_PATTERNS` (`:811-816`). Each false positive costs one acting pass.
- `isLikelyLeadIn` (`finalization-guard.ts:62-80`): any answer ≤260 chars containing `check|look up|inspect|pull up|search|find|update|create|make|verify` without a completion word is replaced after reads by the synthesized evidence text. "You have 3 open tasks; check the Q3 plan for the rest." qualifies.

### 5.8 The `/loop` subpath is a host abstraction with one host

`loop/index.ts:3-8` explains the subpath exists "so the web route and the worker provider cannot drift". The web route is deleted. Three injection slots exist only to cross the package boundary: `tool-catalog.ts:26-50` (globalThis Symbol), `skill-lookup.ts:19-33` (closure, never read), `tool-payload-compaction.ts:69-92` (globalThis Symbol). The worker installs them at module load (`provider/tool-surface.ts:77, 83`). Web's live `/loop` imports are ≈12 symbols across 19 files (sanitizer, research-log constants, stated-future constants, `extractContextShiftPayload`, `classifyToolTraceName`, the pending-contract readers, `searchTelemetryColumns`, two type-only imports).
