## 3. Recurring themes, counts, and what actually cures each

Counts are turns (not cases) across R0–R5 plus the four non-battery sessions, from the receipts above.

### 3.1 The contract/review lane blocks or damages well-specified writes — 19 turns

R0 ×4 (`734aa3dd`, `d1138b88`, `2778b1a2`, `7d547888`), R1 ×4 (`34d0f1f2`, `c131544f`, `cb89f945`, `b06d4650`), R2 ×3 (`069c45f4`, `b7b715f6`, `579e0c95`), R3 ×2 (`259f6a28` two corrupt revisions, `f9640b74` false unfulfilled), R4 ×4 (`bd67667d`, `f0c2b495`, `aacf658a`, `78adb24c`), `41e496f7`, Book-QA `258954cd`.

Three distinct sub-causes: (a) the reviewer is asked to restate content inside short schema fields (160/240/400 chars) and, being a model, fills them to the cap with garbage (`##2`, `|||||`, zero-width chars, `.Re?`) — six turns; (b) the reviewer's decision fails the harness's own parser (invented fields on 09-02, non-null labels on 09-04) and the harness converts its internal failure into a user question — seven turns; (c) the completion ledger disagrees with the executor about what was written — three turns.

**Cure: (a) less machinery + (b) different machinery.** Sub-cause (a) is structural: a `corrected_contract` that must carry values will always tempt the reviewer to carry prose; de43925ca's demotion fixes the 160-char field but the 240/400-char prose fields still invite the same failure and were "fixed" by prompt text only. The reviewer should return a _verdict about the actor's proposal_ (approve / reject-with-reason / ask-user) and never author a replacement contract; corrections are cheaper and safer as one bounded actor repair pass with the reviewer's reason. Sub-cause (b) is the cost of having two models negotiate a strict schema: every schema change is a live-regression risk on a path unit tests mock (the 298-line `agenticChatRetest20260904Regressions.test.ts` supplies mocked reviewer decisions; the regression was caught only by a browser battery). Sub-cause (c) argues for one source of truth: the executor's write ledger is the completion record; the contract should be checked against it, not re-derived.

### 3.2 The direct-write lane exists but the model never takes it — 11 of 11 single-target edits

Every narrow task update and selective document edit in R1–R4 opened with `declare_turn_contract` (R1 `c131544f`, `f4664727`, `cb89f945`; R2 `b7b715f6`, `c4cb3552`, `579e0c95`; R3 `259f6a28`, `f9640b74`; R4 `bd67667d`, `f0c2b495`, `aacf658a`), including `f0c2b495` where the user typed the UUID and `bd67667d` where `get_onto_task_details` had just returned exactly one task. `update_onto_task` and `update_onto_document` are `directWriteClass: 'ordinary'` / `resolved_existing` (`apps/worker/src/workers/agentic-chat/mutations/tool-catalog.ts:469-470`, `:267-268`), so a read-then-write would have been accepted by `assessDirectWriteBatch` (`write-routing.ts:72-130`) with no reviewer call. Cost of not taking it: 64.8 s / 93.5 s / 83.2 s for two-field edits, a GPT round each, and the entire R4 regression surface.

Two reasons in the prompt: `WORKER_WRITE_TURN_RULE_LINES` (`apps/web/src/lib/services/agentic-chat-lite/prompt/situational-rules.ts:74`) opens with "Writing to an existing entity: call declare_turn_contract first, unless…" — a weak model executes the imperative and skips the exception. And the exception itself overstates the code: the prompt says a target id "was given by the user" qualifies, but `isDeterministicallyResolvedId` (`write-routing.ts:244-262`) requires the user-typed UUID **and** a read this turn that loaded it (`turnSeenEntityIds`). A model that follows the prompt and writes directly with a pasted UUID is withheld and re-routed (`target_resolution_requires_review`, one wasted pass).

**Cure: (c) better prompt, with the code invariant unchanged.** Rewrite the rule as an ordered recipe: read the target → if exactly one match, call the update tool → declare only when several match or the batch is >3/mixed/ordered; and say "typed UUID + one read" to match the code. This is the single cheapest latency win in the evidence.

### 3.3 Clarification validation loops — 4 turns, 5 rejected calls; cured

R1 `7078bc00`, R2 `8a2fcdd3`, R2 `0d8019ca` (×3, fatal), plus the 09-02 long-answer turn. The rule required the question to repeat labels the host renders anyway. Deleted in de43925ca; R3 had zero. **Cure was (a) less machinery** and it worked. Lesson for the rest of the validator set: any control-tool rule that cannot name a user-visible failure it prevents should be deleted, because a cheap model will repeat the identical invalid call rather than parse the error.

### 3.4 Dates shift by a day — ≥12 case-instances in R0–R2; cured deterministically

Three independent paths (UTC-midnight storage of civil dates; UTC instants rendered to the model; overview projecting `null`). All fixed in code in de43925ca; R3/R4 show zero date drift in creates, updates, editors, and fresh-chat reads. **Cure was (b) different machinery** (render in the user's zone, store civil days). No prompt would have fixed it: every model reads `2026-09-23T03:59:59Z` as the 23rd.

### 3.5 Absent records asserted as real-world facts — 5 of 5 owner-report turns; three prompt edits have failed

`cbd55cc6` (R0), `6741cbaa` (R1), `90f7354d` (R2), `a7e21a65` (R3), `9959665d` (R4). R3 and R4 ran with the de43925ca and ef4ad9a rules respectively. The failing sentences are formulaic ("no payments", "not approved", "nothing has been … paid for", "$0 spend"). **Cure: (b) different machinery or (d) better model — not (c).** Three prompt iterations against the same model is enough evidence that a fourth sentence will not move it. Options in rising cost: a deterministic absence-claim linter on report-style answers that rewrites claims with no supporting record to "not recorded"; a small judge pass only when the user asked for a status/report and the answer contains absence claims; or routing report turns to the reviewer model. The battery's own case 14 judge (`case-14-grounded-status.scenario.ts:100-127`) is the right shape for the eval.

### 3.6 Document fidelity (verbatim storage, stored dates, edit preservation) — 7 turns in R0–R2; cured by prompt (n=1)

R0/R1/R2 c9 stripped the injection payload (3 turns); R2 c7 rewrote the changelog date; R0/R1/R2 c8 never reached the write (see 3.1). R3 passed all three exactly. The two prompt fixes (`build-lite-prompt.ts:110`, `:1366-1370`) are the only thing standing between a model and silently editing a user's quoted text. **Cure: (b) different machinery is available and cheap** — for a create whose user message contains a quoted or fenced block, byte-compare the stored body to that block in the executor and either repair or disclose the difference. The battery already does this comparison offline; the product should do it inline.

### 3.7 General Chat vs Project Setup asymmetry — 1 case live, but the surface still has holes

R2 c1 is the only measured instance and is fixed (`surfaces.ts:108`). But the same shape remains for other tools: `create_onto_document`, `update_onto_document`, `link_onto_entities`, `list_onto_documents`, `get_document_tree` are project-surface only (`surfaces.ts:128-146`). A General Chat request "add a note to project X" or "make task A depend on task B" has no tool to call and will produce the R2-`407d881c` shape ("the tool is not available"). No battery exercises this because the browser battery ran document cases in project context and the automated Cedar House battery never uses the global surface at all (`cedar-house.test.ts:66` restricts turns to `project` / `project_create`; `case-01-project-create.scenario.ts:49`). **Cure: (a) fewer surfaces** — mount the document write pair and relationship tool globally with `project_id` required, or accept the gap and say so in the prompt. Untested is the real problem.

### 3.8 Calendar credentials on the worker — 4 of 5 runs failed; never passed on the worker path

R0 fail ×2, R1 **pass on the deleted web engine**, R2 `provider_error`, R3 `credentials_not_configured`, R4 `credentials_unreadable`. Until they are set, case 10/12 measure Railway, not the agent, and the one-engine migration has removed the only path that ever read a calendar.

### 3.9 Cheap-route transport flakiness — 25 failed acting passes in 48 turns

R1: 10 failed passes/17 turns (404 `No endpoints found for deepseek/deepseek-v4-flash(-20260423)` ×4, 429 ×3, 60 s timeout ×2, `tool_calls while tool_choice=none` ×1); R2: 9/17; R3: 6/14; R5: 1. ### 3.10 Latency: 5–8 acting passes for one-entity turns

R3 assessment §6: cabinet update 93.5 s = 5 acting attempts / 80.5 s + 1 review / 4.1 s; ambiguity 99.1 s = 6 attempts / 86 s; doc edit 83.2 s = 8 attempts / 46.7 s + 3 reviews / 23 s; owner report 68 s = 7 attempts. ### 3.11 Over-reading and read loops — 8 turns

R0 `cbd55cc6` (18 reads), `3329d98f` (15, no answer), R2 `90f7354d` (11, one `anchor` missing), R3 `a7e21a65` (14: anchor `"-"`, two redundant `search_all_projects`), R3 `5792be5e` (3 serial task reads for a 2-way ambiguity), R3 `a1a85bdf`/`65d9d292` (`read_document_section` on a no-heading doc → told to use a tool not on the surface), `41e496f7` (re-reading a document already in the prompt), `177eaae4` (prompt falsely said the focused document was truncated). ## 4. What the evidence says about the cheap-model thesis

Per failure, would a stronger acting model have avoided it with the same harness, or is it harness-caused and would break any model?

**Harness-caused; any model breaks (fixes were code, and the same model then passed):**

- Date drift (3.4): the model was shown UTC instants. Fixed in code → R3 100% correct with the same model.
- 160-char prose cap → `##2`, `|||||` (3.1a): the _strong_ model (GPT-5.6-luna, the reviewer) produced the corruption. A stronger actor changes nothing here; the reviewer is already the strong model.
- Reviewer label-null schema (R4): again the strong model's output rejected by the harness's parser.
- Verbatim-label clarification rule (3.3): removed; same model passed c11 in 16 s with zero tools.
- Surface omissions (`create_onto_project`, `link_onto_entities`, `get_onto_document_details`, `delete_calendar_event` on the cleanup turn): no model can call a tool it is not given; four cases lost points to this.
- Completion ledger vocabulary (`duration_minutes`), plan mismatch after reviewer correction, feedback-kind crash, calendar credentials, egress block after a workspace read, focused-doc truncation math: pure code.
- `calendar_sync` defaulting to create an event on a task update (R1 c4): a default that violates the user's stated constraint; the model omitted the argument, the harness chose the destructive default.

**Cheap-model-specific (a stronger actor would likely have avoided; the harness has compensating machinery whose cost is measurable):**

- Repeating an identical invalid call three times despite an error that named the fix (R2 `0d8019ca`; 09-02 DeepInfra ×3). The third-pass "switch route on repeated identical failure" detector exists only because of this.
- Repetition degeneration: 50 copies of the same UUID in `target_ids` (R4 `bd67667d`).
- `tool_calls` while `tool_choice=none` (R1 `8662cc0d`, 09-02) — a protocol violation that required its own recovery branch.
- Minimal contracts with no `required_fields`/`changes` (R4, `41e496f7`) — the reviewer exists partly to repair these; that is a GPT round per complex write to compensate for the actor.
- Over-reading and serial single-tool passes (3.11), re-reading a document already in context.
- Declaring instead of taking the direct lane (3.2) — the prompt leads it there, but a stronger model would more often notice the exception.
- Absence → assertion in reports (3.5): persists across three prompts; plausibly model capability. Note the reviewer model is never consulted on read turns, so the "strong model" has never been tried on this case.
- Inventing an OAuth explanation for a calendar failure (R2 c10) and inferring a stored prerequisite from a search hit (R1 c6).

**Verdict.** The 27 → 45 jump was achieved with the same cheap model by removing harness faults, which supports the thesis. But the residual failures split cleanly: the _write_ path's remaining failures are harness-caused (reviewer content-carrying, schema negotiation between two models, direct lane never reached), while the _read/report_ path's remaining failures are model-flavored (grounding, over-reading). The evidence does not support "a better prompt fixes the report case"; it supports either a deterministic post-check or spending the reviewer model there. It also shows the reviewer is not free of the failure modes it guards against: the strong model corrupted content in three runs and its schema drift caused the worst single regression.

## 8. What is right and must not be undone

- The deterministic fixes in de43925ca did exactly what a harness should: same model, +18 points, no extra passes. In particular timezone projection in `read-result-timezone.ts`, the prose-field demotion in `turn-contract.ts:325-365`, and deleting the verbatim-label rule.
- The direct-write floor (`write-routing.ts:72-130`) is correct and safe; the problem is that the prompt never lets the model reach it (I2), not the gate.
- Honest failure over fabricated success: from R1 onward the agent says what it could not do (calendar, dependencies, blocked edits). R0's "promised edit that never happened" did not recur.
- The candidate-ambiguity floor caught real ambiguity (R1/R2/R3 case 5) every time; its false positives are all the Context Document (I6), not the mechanism.
- The batteries themselves: fixed prompts, fixed rubric, independent SQL verification, separated first attempt from recovery. They found every regression the unit suites missed. Keep running them; make them cheaper to run (I7).
- The hostile-source boundary held in all five runs: the injected `<system_override>` never executed.
- `renderWriteReceiptFallback` and the structured `rejectionCode` diagnostics — the two things R4 proved were missing — are now in HEAD; do not trade them away in a simplification pass.
