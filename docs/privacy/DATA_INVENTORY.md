# BuildOS data inventory

This file lists every place BuildOS stores personal data or sends it to a third party. For each one it
says what keeps the data there and how the data goes away. It is tasker 103, deliverable 1, as of
2026-09-24. The sibling file [CLAIMS.md](CLAIMS.md) maps each sentence on `/privacy` to code.

## How to use this file

- Find the store (a table, bucket, or outside service) in its area table. **Class** tells you which rule
  applies. **Retention** names the code that enforces it.
- When you change a store, a window, or a processor, update its row here in the same commit. Update the
  matching CLAIMS.md row too.
- Account deletion sweeps a new table automatically if it is keyed by `user_id`. It does not sweep a new
  table without `user_id`, and a new NO ACTION or RESTRICT reference to a user blocks the purge (see
  [Deletion](#deletion)).
- Line numbers drift. Symbol and migration names are the stable reference.

**Classes**

- **WORKSPACE:** the user built it. Kept until the user deletes it, or deletes the account.
- **PASS-THROUGH:** read on the user's behalf: Gmail, Google events BuildOS didn't create, web pages,
  model calls. Used during the request and not kept. At most, a content-free trace is kept: ids, counts,
  times, hashes, scores.
- **DERIVED:** a diagnostic, trace, cache, or copy. It has a named expiry. That is either a fixed window or
  "with parent", for copies that exist only alongside a workspace item or the account.

**True on deploy.** These rows describe the code after the tasker 103 migrations are applied and web and
worker ship from one commit. Until then, parts of this file are false in production. The conditions and the
migration order are in [CLAIMS.md → True-on-deploy conditions](CLAIMS.md). Two DJ decisions are still being
built. This file describes them as their final state:

- **Task archive:** `20260924190350_task_archive_state.sql`.
- **Minimal calendar-analysis events:** `20260924190500_calendar_analysis_minimal_events.sql`.

**Who can read**

- Every `public` table has RLS on (production catalog check, 2026-09-24).
- **Owner:** the user reads their own rows through the user-scoped client. Policies on tables older than the
  migration history exist only in production.
- **Members:** project members, via `current_actor_has_project_access` or
  `current_actor_has_project_member_access`.
- **Service:** service-role clients (worker, crons, server routes).
- **Admin:** the named admin routes. When an admin opens or exports another user's chat, the request goes
  through `apps/web/src/lib/server/admin-chat-content-access.ts`. It projects pass-through rows, fails closed,
  and writes each access to `security_events`.

Every database table and bucket is hosted by Supabase. Vendor terms are linked in [Processors](#processors).

## Deletion

### Item delete

This covers projects, docs, tasks, goals, plans, milestones, risks, requirements, events, assets, comments,
contacts, profile docs, voice notes, cycles, and calendar connections.

- **At delete:** `deleted_at` is set, and the item leaves the workspace at once. For 30 days it can be
  restored; for tasks, through `POST /api/onto/tasks/[id]/restore`. A voice note's audio is removed right away.
- **30 days later,** PURGE erases it in two steps:
    - Storage objects go first. A row waits until its object is gone.
    - Then the row goes, along with its embeddings, edges, log rows, comments, versions, proposals, public pages,
      event-sync rows, and every tree snapshot that lists it.
- **A project** goes with everything inside it, through `delete_onto_project`. Its Google-mapped events are
  deleted from Google by queued `sync_calendar` jobs. Google emails a cancellation to any attendees.
- **Pointers from live rows are nulled, not deleted.** This covers a task's `plan_id`, a project's
  `context_document_id`, and `calendar_source_id`. Notification events of a purged project lose
  `project_name`.
- **Failures** are recorded in `privacy_purge_failures` and retried after 20 hours. A failure never blocks
  other rows.

### Task archive

ARCHIVE changes what Archived means:

- Dragging a task to Archived sets `archived_at`.
- The task stays in the Archived column with no time limit. The purge never touches it.
- Deleting a task, archived or not, is a real delete, and the task is erased 30 days later.

### Chat delete

A chat delete is immediate; there is no 30-day wait.

- `delete_my_chat_session` (DEL) erases the chat, its messages, and every worker turn row in one transaction.
  That includes effects in any state. Rows keyed to the session cascade.
- It refuses with 409 while a turn is queued or running. Another user's chat returns 404.
- Attached chat images become orphans, and the next Job run removes them.
- Two things survive:
    - voice notes recorded in the chat, because their group is unlinked, not deleted;
    - `llm_usage_logs` rows, which hold no text.

### Disconnect Gmail or Calendar

- **Gmail:** revoked at Google, then the connection and credentials are hard-deleted.
- **Multi-calendar:** revoked at Google, soft-deleted, then erased by PURGE at 30 days.
- **Legacy calendar:** revoked at Google, then deleted. The webhook channel is stopped first.

### Account deletion request

Everything below happens in the same transaction as the request (`request_account_deletion` →
`lock_account_for_deletion`).

- **Sign-in:** the user is signed out, and sign-in is blocked (`deletion_status='pending'`, `access_restricted`).
- **Google:** Gmail and Calendar are revoked at Google and deleted, and calendar sync stops.
- **Agents:** agent keys and OAuth grants are revoked. Access tokens are revoked, and refresh tokens and codes
  are expired. `caller-auth.ts` and the MCP token check both refuse the account.
- **Background work stops:** briefs, notifications, SMS, push, lifecycle emails, scheduled agents, and pending
  queue jobs. The worker scheduler also skips the account.
- **Public pages:** pages the user published, and every page in a project the purge will delete, go offline.
- **Billing:** the Stripe subscription is set to cancel at period end.

### Account purge

The hourly cron runs the purge when it is due, 29 days 23 hours after the request. The steps run in this order:

1. The Stripe subscription is cancelled immediately.
2. The Gmail and Calendar cleanup runs again.
3. Storage objects are removed. This covers voice notes, brief audio, email attachments, any
   `<user_id>/` or `users/<user_id>/` path (data exports included), assets of projects only the user owns,
   and the Libri objects in scope.
4. LIBRI `libri.purge_account_deletion` runs.
5. `finalize_account_deletion_database` runs. It deletes the projects only this user owns, every chat and
   turn row, agent runs and their cost ledger, cycles, the user's activity-log rows, and system emails sent to
   them. It also deletes legacy project history, research evidence that came only from them, and their beta
   signup. Finally it sweeps every row keyed by their `user_id`. Along the way it:
    - anonymizes their actor to "Deleted user";
    - regenerates the slug prefix of pages that survive;
    - scrubs event bodies that name them.
6. `auth.admin.deleteUser` runs.
7. The PostHog person is deleted. The outcome is stored in `posthog_deletion_status`.

A failed purge is retried every hour, and the cron logs `status='error'`. Once a request is more than 24
hours overdue, every run writes a critical `security_events` row (`account_deletion.deadline_missed`).

### What survives, and why

- **Consent records** (`legal_acceptances`): proof of what the user agreed to.
- **`account_deletion_requests`:** the audit row that shows the deletion ran.
- **The Stripe customer and invoices at Stripe** (DJ decision). The local `webhook_events` payloads
  age out after 90 days.
- **Emails already sent:** they stay in the recipient's inbox and in the sending Workspace mailbox.
  `email_suppressions` rows stay so opt-outs keep working.
- **Twilio's own delivery logs.**
- **Contributions in shared projects**, credited to "Deleted user". The user's own words stay as written.
- **`security_events`**, with the actor id nulled and bodies scrubbed, until their 180- or 400-day window ends.
- **Rows not tied to an account:**
    - `visitors` (IP and UA are gone after 30 d);
    - `native_search_cache` (expires within a day);
    - views of other people's pages (90 d).
- **Data outside the database:**
    - Railway and Vercel log lines, until the vendor rolls them off;
    - OpenAI voice data, for up to 30 days;
    - Supabase backups, until they roll off. If a backup is ever restored, the page promises to delete the user's
      data again; that step is a manual runbook.
- **PostHog data, if the PostHog env vars are missing.** The purge then records `skipped`.
- **Things an item delete leaves behind today** (Open items):
    - a chat's voice notes;
    - the children of a deleted folder document;
    - `agent_runs`, `homework_runs`, `agent_operatives`, and chats that mention a purged project.
